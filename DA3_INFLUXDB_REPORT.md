## 1. Executive Summary & Problem Formulation

In a Smart Home / IoT device monitoring platform, data workloads naturally divide into two fundamentally divergent access paradigms:

1. **Transactional Metadata (Relational):** Highly structured entities exhibiting complex foreign-key relationships, role-based access control, cascading triggers, and strict ACID guarantees (e.g. `USERS`, `HOMES`, `HOME_ACCESS`, `ROOMS`, `DEVICES`, and `AUTOMATION_RULES`).
2. **High-Velocity Telemetry Stream (Time-Series):** Continuous, timestamped numerical observations generated by sensors (temperature, humidity, motion events, power draw) arriving every second or minute per device.

### The Relational Bottleneck (Oracle 21c RDBMS)
In the original architecture, all telemetric observations were ingested into the Oracle table `SENSOR_READINGS (device_id, reading_id, value, reading_time)`. As the system scales to thousands of homes and hundreds of thousands of devices, traditional relational database engines encounter severe bottlenecks:
- **Write Amplification & Lock Contention:** Inserting millions of sequential readings requires continuous updates to B-Tree indexes on composite primary keys `(device_id, reading_id)` and timestamp columns. Row-level transaction logging (Undo/Redo logs) causes disk I/O thrashing.
- **Absence of Native Downsampling & Auto-Retention:** Relational databases treat all rows uniformly. Purging aged raw telemetry requires expensive `DELETE` queries that cause table fragmentation and lock escalation, or complex custom partition management (`DBMS_SCHEDULER`).
- **Heavy Analytical Aggregations:** Calculating moving averages, rollups, and anomaly detection in SQL requires expensive full-table partition scans, nested CTEs, and window functions (`OVER (PARTITION BY ... ORDER BY ...)`).

### The Solution: Polyglot Persistence
To solve this, we extend the mini-project with **InfluxDB 2.7**, establishing a **Polyglot Persistence Architecture**:
- **Oracle 21c XE** remains the authoritative source of truth for all transactional business entities.
- **InfluxDB 2.7** offloads the continuous, append-only time-series telemetry streams, leveraging **Time-Structured Merge Trees (TSM)** and **Gorilla float64 compression**.

### Selected Category: Time-Series Database (TSDB)
### Selected Technology: InfluxDB 2.7.11 (Alpine)

Among the approved modern database categories, a Time-Series Database is mathematically and architecturally the most optimal choice for IoT telemetry:

| :--- | :--- | :--- | :--- |

## 3. Data Model & Schema Transformation

### 3.1 Relational Schema (Oracle 3NF)
In Oracle 21c, sensor observations are stored across normalized tables:
```sql
CREATE TABLE SENSOR_READINGS (
    device_id    NUMBER NOT NULL,
    reading_id   NUMBER NOT NULL,
    value        NUMBER(6,2) NOT NULL,
    reading_time TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL,
    CONSTRAINT pk_sensor_readings PRIMARY KEY (device_id, reading_id),
    CONSTRAINT fk_readings_device FOREIGN KEY (device_id) REFERENCES DEVICES(device_id)
);
```

### 3.2 InfluxDB Line Protocol Data Model
In InfluxDB, the normalized schema is mapped into a multi-dimensional time-series data point composed of:
1. **Measurement (Table equivalent):** `sensor_reading`
2. **Tag Set (Indexed String Metadata):** `device_id`, `device_name`, `device_subtype`, `unit`
3. **Field Set (Unindexed Numeric Metrics):** `value`
4. **Timestamp:** Nanosecond Unix Epoch (`1726599600000000000`)

```text
sensor_reading,device_id=4,device_name=Kitchen\ Temp\ Sensor,device_subtype=TEMPERATURE_SENSOR,unit=CELSIUS value=23.50 1726599600000000000
sensor_reading,device_id=5,device_name=Living\ Room\ Sensor,device_subtype=TEMPERATURE_SENSOR,unit=CELSIUS value=24.10 1726603200000000000
```

## 5. Section 5: Analytical Querying & Live Benchmarking

### 5.1 Query Language Comparison (SQL vs Flux)

#### Task: Calculate 1-Hour Rolling Averages for Device 4
**Oracle 21c SQL:**
```sql
SELECT 
    TRUNC(reading_time, 'HH') AS time_bucket,
    ROUND(AVG(value), 2) AS avg_temperature,
    COUNT(*) AS sample_count
FROM sensor_readings
WHERE device_id = 4
  AND reading_time >= SYSDATE - 30
GROUP BY TRUNC(reading_time, 'HH')
ORDER BY time_bucket ASC;
```

**InfluxDB Flux Pipeline:**
```flux
from(bucket: "sensor_telemetry")
  |> range(start: -30d)
  |> filter(fn: (r) => r["_measurement"] == "sensor_reading" and r["device_id"] == "4")
  |> filter(fn: (r) => r["_field"] == "value")
  |> aggregateWindow(every: 1h, fn: mean, createEmpty: false)
  |> yield(name: "hourly_mean")
```

- The interactive frontend provides non-technical homeowners with intuitive telemetry visualizations while equipping systems engineers with a full-fledged Flux analytics console and live performance benchmarks.
